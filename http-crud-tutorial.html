Módulo 2

Fundamentos de HTTP

Antes de escrever código, é preciso entender o protocolo que faz a web funcionar. Tudo que o frontend faz com a API é, no fundo, enviar requisições HTTP e ler respostas HTTP.

O que é HTTP?

HTTP (HyperText Transfer Protocol) é o protocolo que o navegador usa para conversar com servidores. Toda vez que você acessa um site, clica num link ou envia um formulário, o navegador manda uma requisição e recebe uma resposta.

fluxo
  Navegador (cliente)                          Servidor (backend)
  ───────────────────                          ──────────────────
        │   "me dá a lista de usuários"                │
        │  ─────────── requisição HTTP ──────────────▶ │
        │                                         processa...
        │  ◀────────── resposta HTTP ───────────────── │
        │   "aqui: [{ name: 'Victor' }, ...]"          │

Uma requisição tem

  • URL — para onde vai (ex: localhost:8000/api/users)
  • Método — o que fazer (GET, POST, PUT, PATCH, DELETE)
  • Headers — metadados (ex: Content-Type)
  • Body — dados enviados (só em POST, PUT, PATCH)

Uma resposta tem

  • Status code — deu certo? (200, 404, 500…)
  • Headers — metadados da resposta
  • Body — os dados retornados (geralmente JSON)

O que é uma API REST?

API é uma interface que permite dois programas conversarem. REST é um conjunto de regras para organizar essa conversa usando HTTP. A ideia central: tudo é um recurso (resource) — usuários, produtos, posts… Cada recurso tem uma URL (endpoint), e o método diz o que fazer com ele.

Método + URLO que significa
GET /api/users“me dá a lista de todos os usuários”
GET /api/users?id=1“me dá o usuário 1”
POST /api/users“cria um novo usuário”
PUT /api/users?id=1“substitui o usuário 1 inteiro”
PATCH /api/users?id=1“atualiza só alguns campos do usuário 1”
DELETE /api/users?id=1“deleta o usuário 1”

A URL diz qual recurso. O método diz o que fazer com ele.

Convenções REST

  • GET nunca muda dados no servidor — é só leitura.
  • PUT e DELETE são idempotentes — repetir a requisição dá sempre o mesmo resultado.
  • POST não é idempotente — cada POST cria um novo recurso.
💡 Idempotência na prática DELETE /users/1 três vezes → o usuário 1 continua deletado. PUT /users/1 três vezes → sempre o mesmo resultado. Mas POST /users três vezes → 3 usuários criados!

O que é JSON?

JSON (JavaScript Object Notation) é o formato padrão de troca de dados entre frontend e backend. Aceita: string, number, boolean, null, array e object.

json
{
  "name": "Victor",
  "age": 24,
  "email": "victor@email.com",
  "hobbies": ["música", "programação"],
  "active": true
}

JSON.stringify() — objeto → string

js
const user = { name: "Victor", age: 24 };
JSON.stringify(user);
// '{"name":"Victor","age":24}'  ← STRING

O fetch() só aceita strings no body — por isso o stringify.

JSON.parse() — string → objeto

js
const json = '{"name":"Victor","age":24}';
JSON.parse(json);
// { name: "Victor", age: 24 }  ← OBJETO

response.json() já faz o JSON.parse automaticamente.

fetch() e async/await

O fetch() é a função nativa do JavaScript para requisições HTTP. Ela retorna uma Promise — o resultado não vem na hora, porque a requisição precisa ir até o servidor e voltar. Por isso usamos await, que “pausa” a execução até a resposta chegar. E await só funciona dentro de uma função async.

js
async function loadUsers() {
  const response = await fetch("http://localhost:8000/api/users");
  const data = await response.json();
  console.log(data);
}

O fluxo de toda requisição fetch

  1. fetch(url, opções) → envia a requisição
  2. await → espera a resposta chegar
  3. response → objeto Response (status, headers, body como stream)
  4. await response.json() → lê o stream e converte para objeto JS
  5. data → o objeto/array que o servidor retornou

Cada método na prática

GET — buscar dados

Lê/lista recursos. Não envia body. Sem o segundo argumento, o fetch assume GET. Filtros vão na URL como query string.

js
const response = await fetch("http://localhost:8000/api/users");
const data = await response.json();

// filtrando pela URL:
fetch("http://localhost:8000/api/users?id=1");
fetch("http://localhost:8000/api/users?age=25&name=Victor");

POST — criar dados

Cria um novo recurso. Envia os dados no body. O header Content-Type: application/json é obrigatório — sem ele o servidor não sabe o formato do body.

js
const response = await fetch("http://localhost:8000/api/users", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: "João", age: 25, email: "joao@email.com" }),
});
const created = await response.json();

PUT — substituição completa

Substitui o recurso inteiro. Você envia todos os campos, mesmo os que não mudaram — se omitir um, ele some. A URL (?id=1) diz qual recurso; o body diz o que colocar no lugar.

js
const response = await fetch("http://localhost:8000/api/users?id=1", {
  method: "PUT",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: "Victor", age: 25, email: "novo@email.com" }),
});

PATCH — atualização parcial

Atualiza apenas alguns campos, sem enviar tudo. O resto permanece como estava.

js
const response = await fetch("http://localhost:8000/api/users?id=1", {
  method: "PATCH",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ age: 30 }),
});
💡 PUT vs PATCH PUT é como reescrever a folha inteira. PATCH é como usar corretivo só onde precisa.

DELETE — remover

Exclui um recurso. Geralmente sem body — o ?id=1 na URL já diz qual apagar.

js
const response = await fetch("http://localhost:8000/api/users?id=1", {
  method: "DELETE",
});

OPTIONS — o preflight do CORS

Quando o frontend (:8080) chama a API (:8000), são origens diferentes. Por segurança, o navegador faz antes uma requisição OPTIONS perguntando “posso te fazer requisições?”. Isso é o CORS (Cross-Origin Resource Sharing).

preflight
1. Navegador → servidor:  OPTIONS /api/users   "posso fazer POST com JSON?"
2. Servidor → navegador:  204 + headers CORS   "sim, pode"
3. Navegador → servidor:  POST /api/users      (a requisição real)
4. Servidor → navegador:  201 Created          (a resposta real)
⚠ Você NÃO escreve código para OPTIONS O navegador faz isso sozinho, automaticamente. Você nunca vai ver um fetch com method: 'OPTIONS'. O preflight dispara para métodos “não-simples” (PUT, PATCH, DELETE) ou quando há header como Content-Type: application/json — então até o seu POST dispara.

Tratamento de erros

Detalhe crucial: o fetch() não lança erro quando o servidor retorna 400, 404, 500… Ele só lança quando a requisição nem chega ao servidor (sem internet, servidor caiu, URL inválida). Por isso você precisa verificar response.ok manualmente.

js
try {
  const response = await fetch("http://localhost:8000/api/users");

  if (!response.ok) {
    // servidor respondeu com erro (400, 404, 500...)
    const error = await response.json();
    console.error("Erro do servidor:", error.error);
    return;
  }

  const data = await response.json();
  console.log(data);
} catch (error) {
  // o fetch nem conseguiu conectar (erro de rede)
  console.error("Erro de rede:", error.message);
}

try/catch pega

  • Sem internet
  • Servidor offline
  • URL inválida
  • Timeout / erro de CORS

response.ok pega

  • 400 Bad Request
  • 404 Not Found
  • 405 Method Not Allowed
  • 500 Internal Server Error

A API PHP por dentro

Agora vamos construir o backend: uma API REST em PHP puro, organizada em camadas. Cada arquivo tem uma única responsabilidade, e toda requisição atravessa essas camadas em ordem — do index.php que recebe o request até o data.json que guarda os dados. Vamos criar arquivo por arquivo, seguindo esse caminho.

A arquitetura em camadas

Em vez de um arquivo gigante que faz tudo, o código é dividido em camadas — e cada uma só conhece a próxima. Isso deixa o projeto fácil de entender, testar e modificar: se a validação mudar, você mexe só em validation.php; se um dia trocar o JSON por um banco de verdade, mexe só em data.php.

1. Configuração — config/config.php

Começamos pela configuração: onde ficam os dados e quais origens podem chamar a API (o CORS que vimos no módulo HTTP).

config/config.php
<?php

$dataFile = __DIR__ . '/../../data/data.json';

$allowedOrigins = [
    'http://0.0.0.0:8080', 'http://localhost:8080', 'http://127.0.0.1:8080',
    'http://0.0.0.0:5500', 'http://localhost:5500', 'http://127.0.0.1:5500',
];

$dataFile aponta para o data.json. $allowedOrigins lista as URLs de frontend autorizadas — 8080 é o nosso frontend e 5500 é o Live Server do VS Code. Requisições de origens fora da lista não recebem os headers de CORS e são bloqueadas pelo navegador.

2. O entry point — public/index.php

Todo request entra por aqui. Este arquivo faz três coisas, nesta ordem: (1) aplica os headers de CORS, (2) responde ao preflight OPTIONS, e (3) roteia pela URL.

public/index.php
<?php

require_once __DIR__ . '/../config/config.php';
require_once __DIR__ . '/openapi.php';

$origin = $_SERVER['HTTP_ORIGIN'] ?? '';

in_array($origin, $allowedOrigins) ?
    header("Access-Control-Allow-Origin: $origin") : null;
header('Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, OPTIONS');
header('Access-Control-Allow-Headers: Content-Type');

if ($_SERVER['REQUEST_METHOD'] === 'OPTIONS') {
    http_response_code(204);
    exit;
}

$uri = strtok($_SERVER['REQUEST_URI'], '?');

match ($uri) {
    '/api/users' => require __DIR__ . '/../src/api.php',
    '/docs' => serveView(__DIR__ . '/../views/docs.html'),
    '/openapi.json' => serveJson(__DIR__ . '/../openapi.json'),
    default => notFound(),
};

function notFound(): void
{
    http_response_code(404);
    echo json_encode(['error' => 'Not found']);
}
  • CORS: se a Origin da requisição está na whitelist, devolve o header Access-Control-Allow-Origin. Os métodos e o header Content-Type são sempre liberados.
  • Preflight: se o método é OPTIONS, responde 204 No Content e encerra com exit — o navegador só queria checar permissão, não há o que processar.
  • Roteamento: strtok($uri, '?') corta a query string (/api/users?id=1 vira /api/users) e o match direciona para o api.php ou responde 404.
E o openapi.php? O projeto de referência também serve uma documentação em /docs (funções serveView/serveJson). É opcional — para o CRUD funcionar, só a rota /api/users importa. Se não quiser as docs, remova essas duas linhas do match e o require do openapi.php.

3. Dispatch por método — src/api.php

A URL já foi resolvida; agora precisamos saber o que fazer. Este arquivo olha o método HTTP e chama o handler correspondente. Métodos não suportados caem no 405.

src/api.php
<?php

require_once __DIR__ . '/controllers.php';

$method = $_SERVER['REQUEST_METHOD'];

match ($method) {
    'GET' => handleGet($dataFile),
    'POST' => handlePost($dataFile),
    'PUT' => handlePut($dataFile),
    'PATCH' => handlePatch($dataFile),
    'DELETE' => handleDelete($dataFile),
    default => handleMethodNotAllowed(),
};

Repare que $dataFile vem do config.php (carregado lá no index.php) e é passado adiante para cada handler. A partir daqui, cada método segue seu próprio caminho pelas camadas.

4. Os controllers — src/controllers.php

O controller é a ponte entre o HTTP e a lógica. Cada handler segue o mesmo roteiro: lê a entrada (body JSON e/ou id da URL), chama o serviço e responde. A função respond() centraliza o envio da resposta.

controllers.php
<?php

require_once __DIR__ . '/services.php';

function respond(array $result): void
{
    http_response_code($result['status']);

    if (isset($result['error'])) {
        echo json_encode(['error' => $result['error']]);
    } else {
        echo json_encode($result['data']);
    }
}

respond() recebe um array com status e (data ou error). Ele define o código HTTP e imprime o JSON certo. Todos os serviços retornam nesse formato — por isso o controller fica tão enxuto.

controllers.php
function handleGet(string $dataFile): void
{
    try {
        echo json_encode(getAllUsers($dataFile));
    } catch (\Throwable $e) {
        http_response_code(500);
        echo json_encode(['error' => 'Internal server error']);
    }
}

function handlePost(string $dataFile): void
{
    try {
        $input = json_decode(file_get_contents('php://input'), true);
        respond(createUser($dataFile, $input));
    } catch (\Throwable $e) {
        http_response_code(500);
        echo json_encode(['error' => 'Internal server error']);
    }
}
  • GET não tem body nem id: chama getAllUsers() e imprime o resultado direto.
  • POST lê o corpo com file_get_contents('php://input') e json_decode(..., true) — o true devolve um array associativo em vez de objeto — e passa ao serviço.
  • O try/catch em cada handler garante que qualquer erro inesperado vire um 500 em JSON, nunca uma tela branca de erro do PHP.

Os handlers de PUT, PATCH e DELETE seguem o mesmo formato, mas extraem o id da query string. O PATCH ainda passa partial: true ao serviço:

controllers.php
function handlePut(string $dataFile): void
{
    try {
        $input = json_decode(file_get_contents('php://input'), true);
        $id = isset($_GET['id']) ? (int) $_GET['id'] : null;
        respond(editUser($dataFile, $id, $input));
    } catch (\Throwable $e) {
        http_response_code(500);
        echo json_encode(['error' => 'Internal server error']);
    }
}

function handlePatch(string $dataFile): void
{
    try {
        $input = json_decode(file_get_contents('php://input'), true);
        $id = isset($_GET['id']) ? (int) $_GET['id'] : null;
        respond(editUser($dataFile, $id, $input, partial: true));
    } catch (\Throwable $e) {
        http_response_code(500);
        echo json_encode(['error' => 'Internal server error']);
    }
}

function handleDelete(string $dataFile): void
{
    try {
        $id = isset($_GET['id']) ? (int) $_GET['id'] : null;
        respond(removeUser($dataFile, $id));
    } catch (\Throwable $e) {
        http_response_code(500);
        echo json_encode(['error' => 'Internal server error']);
    }
}

function handleMethodNotAllowed(): void
{
    http_response_code(405);
    echo json_encode(['error' => 'Method not allowed']);
}
💡 PUT e PATCH usam o mesmo serviço Os dois chamam editUser(). A única diferença é o partial: true do PATCH — que faz a validação pular a exigência de todos os campos. Um só serviço atende os dois métodos.

5. As regras de negócio — src/services.php

Aqui mora a lógica de verdade. Os serviços validam a entrada, decidem o status HTTP e chamam a camada de dados. Todos devolvem o array ['data' => ..., 'status' => ...] (sucesso) ou ['error' => ..., 'status' => ...] (falha) que o respond() entende.

services.php
<?php

require_once __DIR__ . '/validation.php';
require_once __DIR__ . '/data.php';

function getAllUsers(string $dataFile): array
{
    $data = loadData($dataFile);
    return ['users' => $data['users']];
}

function createUser(string $dataFile, ?array $input): array
{
    if (!is_array($input)) {
        return ['error' => 'Invalid JSON body', 'status' => 400];
    }

    $error = validateRequiredFields($input, ['name', 'age', 'email']);
    if ($error) {
        return ['error' => $error, 'status' => 400];
    }

    $error = validateUserFields($input);
    if ($error) {
        return ['error' => $error, 'status' => 400];
    }

    $user = insertUser($dataFile, [
        'name' => trim($input['name']),
        'age' => (int) $input['age'],
        'email' => $input['email'],
    ]);

    return ['data' => $user, 'status' => 201];
}

createUser() é o pipeline completo: confere se o body é um array, valida os campos obrigatórios, valida os valores e só então insere. Cada falha retorna 400 com a mensagem; o sucesso retorna 201 Created com o usuário. Note o (int) $input['age'] — a idade é guardada como número, não string.

services.php
function editUser(string $dataFile, ?int $id, ?array $input, bool $partial = false): array
{
    if ($id === null) {
        return ['error' => 'User id is required', 'status' => 400];
    }

    if (!is_array($input)) {
        return ['error' => 'Invalid JSON body', 'status' => 400];
    }

    if (!$partial) {
        $error = validateRequiredFields($input, ['name', 'age', 'email']);
        if ($error) {
            return ['error' => $error, 'status' => 400];
        }
    }

    $error = validateUserFields($input);
    if ($error) {
        return ['error' => $error, 'status' => 400];
    }

    $allowed = ['name', 'age', 'email'];
    $fields = array_intersect_key($input, array_flip($allowed));

    if (isset($fields['name'])) {
        $fields['name'] = trim($fields['name']);
    }

    if (isset($fields['age'])) {
        $fields['age'] = (int) $fields['age'];
    }

    $user = updateUser($dataFile, $id, $fields);

    if ($user === null) {
        return ['error' => 'User not found', 'status' => 404];
    }

    return ['data' => $user, 'status' => 200];
}
  • PUT e PATCH compartilham este serviço. Quando $partial é false (PUT), exige todos os campos. Quando true (PATCH), pula essa exigência e valida só o que veio.
  • array_intersect_key($input, array_flip($allowed)) é um filtro de segurança: mantém apenas name, age e email, descartando qualquer campo extra que o cliente tente injetar (como um id forjado).
  • Se o updateUser() não encontrar o id, o serviço retorna 404.
services.php
function removeUser(string $dataFile, ?int $id): array
{
    if ($id === null) {
        return ['error' => 'User id is required', 'status' => 400];
    }

    $user = deleteUser($dataFile, $id);

    if ($user === null) {
        return ['error' => 'User not found', 'status' => 404];
    }

    return ['data' => ['deleted' => $user], 'status' => 200];
}

removeUser() exige o id, tenta deletar e devolve o usuário removido dentro de { "deleted": {...} }. Se não existir, 404.

6. A validação — src/validation.php

Duas funções puras: recebem dados e retornam uma mensagem de erro ou null. Separá-las do serviço mantém todas as regras num único lugar.

validation.php
<?php

function validateRequiredFields(array $input, array $fields): ?string
{
    $missing = [];

    foreach ($fields as $field) {
        if (!isset($input[$field])) {
            $missing[] = $field;
        }
    }

    if (!empty($missing)) {
        return implode(', ', $missing) . ' are required';
    }

    return null;
}

function validateUserFields(array $input): ?string
{
    if (isset($input['name'])) {
        $name = trim($input['name']);

        if ($name === '') {
            return 'Name cannot be empty';
        }

        if (strlen($name) > 100) {
            return 'Name must be at most 100 characters';
        }
    }

    if (isset($input['age'])) {
        if (!is_numeric($input['age'])) {
            return 'Age must be a number';
        }

        $age = (int) $input['age'];

        if ($age < 1 || $age > 150) {
            return 'Age must be between 1 and 150';
        }
    }

    if (isset($input['email'])) {
        if (!filter_var($input['email'], FILTER_VALIDATE_EMAIL)) {
            return 'Invalid email format';
        }
    }

    return null;
}
  • validateRequiredFields monta a lista do que falta e devolve algo como "name, age are required". É usada só no POST e no PUT.
  • validateUserFields valida cada campo que existir — por isso serve tanto para a criação completa quanto para o PATCH parcial. O filter_var(..., FILTER_VALIDATE_EMAIL) checa o e-mail sem precisar de regex.

7. A persistência — src/data.php

A camada mais baixa: ninguém mais toca no arquivo. Toda leitura e escrita passa por aqui. Como o "banco" é um JSON, cada operação carrega o arquivo inteiro, mexe no array e grava de volta.

data.php
<?php

function loadData(string $dataFile): array
{
    return json_decode(file_get_contents($dataFile), true);
}

function saveData(string $dataFile, array $data): void
{
    file_put_contents($dataFile, json_encode($data, JSON_PRETTY_PRINT | JSON_UNESCAPED_UNICODE));
}

loadData lê e decodifica o JSON; saveData codifica e grava. O JSON_PRETTY_PRINT mantém o arquivo legível (indentado) e o JSON_UNESCAPED_UNICODE preserva os acentos, gravando João diretamente em vez de convertê-lo para uma sequência de escape Unicode.

data.php
function insertUser(string $dataFile, array $user): array
{
    $data = loadData($dataFile);

    $id = $data['nextId'] ?? 1;
    $data['nextId'] = $id + 1;

    $user['id'] = $id;
    $data['users'][] = $user;

    saveData($dataFile, $data);

    return $user;
}

function updateUser(string $dataFile, int $id, array $fields): ?array
{
    $data = loadData($dataFile);

    foreach ($data['users'] as $index => $user) {
        if ($user['id'] === $id) {
            $data['users'][$index] = array_merge($user, $fields);
            saveData($dataFile, $data);
            return $data['users'][$index];
        }
    }

    return null;
}

function deleteUser(string $dataFile, int $id): ?array
{
    $data = loadData($dataFile);

    foreach ($data['users'] as $index => $user) {
        if ($user['id'] === $id) {
            array_splice($data['users'], $index, 1);
            saveData($dataFile, $data);
            return $user;
        }
    }

    return null;
}
  • insertUser usa nextId como auto-incremento: pega o próximo id, incrementa o contador, carimba o usuário e adiciona ao array.
  • updateUser acha o usuário pelo id e usa array_merge($user, $fields) — os campos novos sobrescrevem os antigos e o que não veio permanece. É isso que faz o PATCH parcial funcionar.
  • deleteUser remove pelo índice com array_splice e devolve o usuário apagado.
  • Retornar null quando o id não existe é o que vira 404 lá no serviço.
⚠ JSON como banco de dados Guardar tudo num arquivo é ótimo para aprender, mas não escala: cada escrita reescreve o arquivo inteiro e não há controle de acesso concorrente. Num projeto real, troque a camada data.php por um banco (SQLite, MySQL, Postgres) — o resto da API não muda, graças à separação em camadas.

O mesmo GET, dos dois jeitos

Com Fetch (nativo)

read.js
export async function getUsers(apiUrl) {
  const response = await fetch(apiUrl);
  const data = await response.json();

  if (!response.ok) {
    throw new Error(data.error || 'Failed to fetch users');
  }
  return data.users;
}

O fetch não lança erro em 400/404/500 — só em falha de rede. Por isso verificamos response.ok e lançamos o erro nós mesmos.

Com Axios

read.js
import axios from 'axios';

export async function getUsers(apiUrl) {
  try {
    const response = await axios.get(apiUrl);
    return response.data.users;
  } catch (error) {
    const message = error.response?.data?.error
      || 'Failed to fetch users';
    throw new Error(message);
  }
}

Sem .json() (o response.data já vem parseado) e erros HTTP caem direto no catch.

PUT e PATCH com Axios

Enviamos o body como um objeto JS direto — o Axios serializa para JSON automaticamente.

import axios from 'axios';

// PUT — atualização completa
export async function putUser(apiUrl, id, user) {
  try {
    const response = await axios.put(`${apiUrl}?id=${id}`, {
      name: user.name,
      age: Number(user.age),
      email: user.email,
    });
    return response.data;
  } catch (error) {
    throw new Error(error.response?.data?.error || 'Failed to update user');
  }
}

// PATCH — atualização parcial
export async function patchUser(apiUrl, id, fields) {
  if (fields.age !== undefined) fields.age = Number(fields.age);
  try {
    const response = await axios.patch(`${apiUrl}?id=${id}`, fields);
    return response.data;
  } catch (error) {
    throw new Error(error.response?.data?.error || 'Failed to patch user');
  }
}

Etapa 4 — Listar usuários (GET)

A primeira funcionalidade: buscar os usuários na API e exibi-los como cards. Precisamos de 3 coisas: (1) uma função que faça GET na API, (2) uma função que transforme os dados em cards, e (3) um gatilho que chame tudo quando a página carregar.

read.js — buscar os dados

O arquivo mais simples da camada de API. Faz um fetch GET (o método padrão), converte para JSON e retorna a lista de usuários.

scripts/api/read.js
export async function getUsers(apiUrl) {
    const response = await fetch(apiUrl);
    const data = await response.json();

    if (!response.ok) {
        throw new Error(data.error || 'Failed to fetch users');
    }

    return data.users;
}
💡 Os pilares export torna a função disponível para outros arquivos. async/await deixa o código assíncrono legível. response.ok é true quando o status HTTP está entre 200 e 299 — lembre que o fetch não lança erro sozinho em 4xx/5xx.

render.js — exibir os cards

Este arquivo cuida do visual. Importa o getUsers, busca os dados e cria um card Bootstrap para cada usuário. Também mantém um cache da última lista, usado depois na edição e na deleção.

scripts/dom/render.js
import { getUsers } from '../api/read.js';

let usersCache = [];

export function findUserById(id) {
    return usersCache.find((user) => user.id === id);
}

export async function renderUsers(apiUrl) {
    const users = await getUsers(apiUrl);
    usersCache = users;
    const usersSection = document.getElementById('users');

    if (users.length === 0) {
        usersSection.innerHTML = '<p class="text-muted">No users found.</p>';
        return;
    }

    usersSection.innerHTML = '';

    users.forEach((user) => {
        const userDiv = document.createElement('div');
        userDiv.classList.add('col-md-3');

        userDiv.innerHTML = `
            <div class="card user-card h-100" id="${user.id}">
                <div class="card-body">
                    <h5 class="card-title">${user.name}</h5>
                    <p class="card-text mb-1"><strong>Age:</strong> ${user.age}</p>
                    <p class="card-text"><strong>Email:</strong> ${user.email}</p>
                </div>
                <div class="card-footer d-flex gap-2">
                    <button class="btn btn-sm btn-outline-dark flex-fill" data-action="edit">Edit</button>
                    <button class="btn btn-sm btn-outline-danger flex-fill" data-action="delete">Delete</button>

}

Etapa 5 — Criar usuários (POST)

Vamos fazer o formulário criar usuários. Envolve capturar o submit, enviar um POST para a API e atualizar a lista.

create.js — enviar os dados

Parecido com o read.js, mas agora com o método POST e um corpo JSON. Note a conversão de age para Number.

scripts/api/create.js
export async function createUser(apiUrl, { name, age, email }) {
    const response = await fetch(apiUrl, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ name, age: Number(age), email }),
    });

    const data = await response.json();

    if (!response.ok) {
        throw new Error(data.error || 'Failed to create user');
    }

    return data;
}
💡 Por que Number(age)? Os inputs HTML sempre retornam strings. A API espera um número para age, então convertemos antes de enviar.

O padrão de tratamento de erro

Todos os arquivos da camada API seguem o mesmo padrão: se response.ok for false, disparam throw new Error(). Isso permite que o app.js use try/catch para exibir a mensagem ao usuário. A API PHP retorna { "error": "mensagem" }, e o data.error extrai esse texto.

Etapa 6 — Deletar (DELETE)

Antes da edição (que é mais complexa), vamos implementar o Delete — e de quebra aprender delegação de eventos.

O que é delegação de eventos?

Os cards são criados dinamicamente pelo JS. Se colocarmos listeners direto nos botões, eles se perdem toda vez que a lista é re-renderizada. A solução: escutar no pai fixo (#users) e descobrir qual filho foi clicado.

💡 Bubbling Quando você clica num botão dentro de #users, o evento "borbulha" (bubble) até o pai. Usamos event.target.dataset.action para saber se foi o botão Edit ou Delete.

delete.js

Envia DELETE com o id na query string. Note que não há body — o id vai na URL.

scripts/api/delete.js
export async function deleteUser(apiUrl, id) {
    const response = await fetch(`${apiUrl}?id=${id}`, {
        method: 'DELETE',
    });

    const data = await response.json();

    if (!response.ok) {
        throw new Error(data.error || 'Failed to delete user');
    }

    return data;
}

Função auxiliar: getUserFromCard

Dado o botão clicado, esta função encontra o card pai e retorna os dados do usuário via cache.

💡 .closest() Sobe na árvore do DOM até achar o ancestral que bate com o seletor. Aqui, encontra o .user-card que contém o botão clicado. O id do card é o id do usuário.

Etapa 7 — Editar (PUT / PATCH)

A funcionalidade mais completa. Envolve um modo de edição, detecção de mudanças e a escolha inteligente entre PUT e PATCH.

PUT vs PATCH — a decisão

PUT substitui o recurso inteiro (envia todos os campos). PATCH atualiza parcialmente (envia só o que mudou). Nosso frontend será esperto: detecta o que mudou e escolhe o método certo.

💡 Eficiência Se o usuário mudou só o e-mail, não faz sentido reenviar nome e idade. O PATCH é mais enxuto e semântico nesse caso.

update.js — duas funções

Este arquivo exporta updateUser (PUT, todos os campos) e patchUser (PATCH, campos parciais).

scripts/api/update.js
// PUT — substituição completa
export async function updateUser(apiUrl, id, { name, age, email }) {
    const response = await fetch(`${apiUrl}?id=${id}`, {
        method: 'PUT',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ name, age: Number(age), email }),
    });

    const data = await response.json();

    if (!response.ok) {
        throw new Error(data.error || 'Failed to update user');
    }

    return data;
}

// PATCH — atualização parcial
export async function patchUser(apiUrl, id, fields) {
    if (fields.age !== undefined) {
        fields.age = Number(fields.age);
    }

    const response = await fetch(`${apiUrl}?id=${id}`, {
        method: 'PATCH',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(fields),
    });

    const data = await response.json();

    if (!response.ok) {
        throw new Error(data.error || 'Failed to patch user');
    }

    return data;
}
💡 fields genérico O patchUser recebe um objeto fields que pode ter 1, 2 ou 3 campos. A conversão de age só acontece se ele estiver presente.

Lógica inteligente no submit

Agora o handler de submit precisa detectar se estamos editando. Se sim, compara campo a campo com o original e decide entre PUT e PATCH. Substitua o conteúdo do try:

app.js
try {
    if (editingId !== null) {
        // === MODO EDIÇÃO ===
        const changed = {};
        if (name !== originalUser.name) changed.name = name;
        if (Number(age) !== originalUser.age) changed.age = age;
        if (email !== originalUser.email) changed.email = email;

        // Nada mudou? Sai da edição.
        if (Object.keys(changed).length === 0) {
            exitEditMode();
            return;
        }

        // Todos mudaram → PUT; alguns → PATCH
        const allChanged = Object.keys(changed).length === 3;

        if (allChanged) {
            await updateUser(apiUrl, editingId, { name, age, email });
        } else {
            await patchUser(apiUrl, editingId, changed);
        }
    } else {
        // === MODO CRIAÇÃO ===
        await createUser(apiUrl, { name, age, email });
    }

    exitEditMode();
    renderUsers(apiUrl);
} catch (error) {
    showError(error.message);
}
💡 A lógica em uma frase 0 campos mudaram → fecha a edição. 1–2 campos → PATCH. 3 campos → PUT. Simples e eficiente.

import axios from 'axios';

export async function getUsers(apiUrl) {

    try {
        const response = await axios.get(apiUrl);
        return response.data.users;
    } catch (error) {
        const message = error.response?.data?.error || 'Failed to fetch users';

    }

}

import axios from 'axios';

export async function putUser(apiUrl, id, user) {
    try {
        const response = await axios.put(`${apiUrl}?id=${id}`, {
            name: user.name,
            age: Number(user.age),
            email: user.email,
        });
        return response.data;
    } catch (error) {
        const message = error.response?.data?.error || 'Failed to update user';
        throw new Error(message);
    }
}

export async function patchUser(apiUrl, id, fields) {
    try {
        const response = await axios.patch(`${apiUrl}?id=${id}`, fields);
        return response.data;
    } catch (error) {
        const message = error.response?.data?.error || 'Failed to patch user';
        throw new Error(message);
    }
}

export async function updateUser(apiUrl, id, user, originalUser) {
    const changedFields = {};
    if (user.name !== originalUser.name) changedFields.name = user.name;
    if (Number(user.age) !== originalUser.age) changedFields.age = Number(user.age);
    if (user.email !== originalUser.email) changedFields.email = user.email;

    if (Object.keys(changedFields).length === 0) return null;

    const allChanged = Object.keys(changedFields).length === 3;
    if (allChanged) {
        return putUser(apiUrl, id, user);
    } else {
        return patchUser(apiUrl, id, changedFields);
    }
}

src/app.js — orquestrador
import { renderUsers } from './scripts/dom/render.js';
import {
    enterEditMode, exitEditMode, getEditingId, getOriginalUser,
    getUserFromCard, showError, hideError,
} from './scripts/dom/form.js';
import { createUser } from './scripts/api/create.js';
import { updateUser } from './scripts/api/update.js';
import { deleteUser } from './scripts/api/delete.js';

const apiUrl = 'http://localhost:8000/api/users';

const form = document.getElementById('create-user-form');
const cancelBtn = document.getElementById('cancel-edit');
const usersSection = document.getElementById('users');

usersSection.addEventListener('click', async (event) => {
    const target = event.target;

    if (target.dataset.action === 'edit') {
        enterEditMode(getUserFromCard(target));
    }

    if (target.dataset.action === 'delete') {
        const user = getUserFromCard(target);
        if (!confirm('Are you sure you want to delete this user?')) return;

        try {
            await deleteUser(apiUrl, user.id);
            if (getEditingId() === user.id) exitEditMode();
            renderUsers(apiUrl);
        } catch (error) {
            showError(error.message);
        }
    }
});

document.addEventListener('DOMContentLoaded', () => renderUsers(apiUrl));
cancelBtn.addEventListener('click', exitEditMode);

form.addEventListener('submit', async (event) => {
    event.preventDefault();

    const name = document.getElementById('name').value;
    const age = document.getElementById('age').value;
    const email = document.getElementById('email').value;

    hideError();

    try {
        const editingId = getEditingId();
        const user = { name, age, email };

        if (editingId !== null) {
            const result = await updateUser(apiUrl, editingId, user, getOriginalUser());
            if (result === null) { exitEditMode(); return; }
        } else {
            await createUser(apiUrl, user);
        }

        exitEditMode();
        renderUsers(apiUrl);
    } catch (error) {
        showError(error.message);
    }
});
